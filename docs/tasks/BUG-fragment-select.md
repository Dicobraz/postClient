## Что происходит

С образа macOS-раннеров GitHub 2026-11-16 (лейбл `macos-26`, понедельничный роллаут) сцена `fragment-select`
стала падать на шаге `input step 2 not done in 30 s` — во всех PR дня (mail-send, html5ever, PLG-02), при
зелёном main и на Windows. Диагностика (×3 со сторожем кадров, run 43875767725): 3/3 падения, **stall кадров
нет**, кадры рисуются до таймаута; область письма в удачном и неудачном прогоне пиксельно одинакова.

Причина (по кадру `-fail` из артефакта прогона 43882653021 и коду): лента беседы грузится из базы фоновой
задачей (`thread::sync_thread` → `reload_thread` → `cx.background_spawn`). Панель чтения сначала рисует письмо
обычным видом, `letter_ready` срабатывает, сцена берёт координаты протяжки (`body.top + LINE`) — и тут приходит
лента: панель перекладывается в режим беседы (сводка, медиа, вложения — над телом), координаты оказываются по
пустому месту. Выделение пустое, `picked()` — `None`, сцена ждёт вечно. Гонка с фоновой задачью: на Windows лента
успевает до фиксации координат, на новых macOS-раннерах (образ 2026-11-16, macOS 26.7.2) — часто после; потому
~50/50 на одном и том же коммите.

## Фикс (ветка fix/screens-drag)

1. Протяжка — по метке первой строки верхнего письма панели (`Selectable` пишет `line-first`), а не по
   пиксельной константе от тела письма: константа попадала по тексту только при удачном сочетании вида беседы,
   картинок и высоты окна (на macOS-раннерах 1024×674 — впритык к сгибу, ~50/50). Wait-хук сцены докручивает
   ленту так, чтобы первая строка была видна (как у поиска, `reveal_at`); `letter_ready` ждёт готовности ленты
   открытого письма (`Feed::ready()`), композер закрыт, документ построен, строка нарисована.
2. `give_up` всегда снимает кадр момента отказа (`<сцена>-fail.png`, в артефакт `screens-macos`) и только потом
   завершает прогон ошибкой: у будущих флаков раннеров сразу будет улика (эта пара кадров и нашла причину).
   Режим `POSTMAN_SCREENS_SHOT_ON_FAIL` («снять и продолжить») не изменился.
