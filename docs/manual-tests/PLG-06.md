# PLG-06. Каталог сертификатов — процессом набора `postman-plugins`

Статус: ⏳ (ручная проверка — владелец; нужен домен с Active Directory и тестовые учётные записи — функциональная
часть поиска сертификатов — `S5-12.5.md`, здесь поведение процесса.)

Подготовка: пакеты PLG-03 кладут `postman-plugins` рядом с `postman` (каталог в общем файле набора — решение
владельца 2026-11-16: почта и каталог вместе); из дерева — `cargo build -p postman-gpui -p postman-plugins`.
Процессы смотреть: Windows — «Подробности» диспетчера задач (`postman-plugins.exe`), Linux — `ps -o pid,rss,cmd -C postman-plugins`.

1. «Настройки → Безопасность → Каталог сертификатов»: подсказка поля «Сервер» — контроллер домена компьютера
   (компьютер в домене — имя контроллера, «не в домене» — подсказка настроек). Контроллер теперь ищет интерфейс
   (функция ОС, `app-gpui/src/sys`), а не плагин: процесса набора в этот момент ещё нет — подсказка не должна
   поднимать `postman-plugins`.
2. Каталог не настроен (сервер пуст, компьютер не в домене): «Проверить» — «каталог не настроен», процесса
   `postman-plugins` нет (плагин не поднимают зря).
3. Настроен сервер (вручную или контроллер): «Проверить» — процесс поднялся после первого кадра (журнал `Debug` —
   строка запуска плагина `ldap`), «найдено N» или отказ каталога — как в `S5-12.5.md`; в журнале — поиск, вход и
   ошибки плагина с меткой `plugin ldap`.
4. Поиск из письма («Конфиденциально», «Найти в каталоге») и при отправке — сертификаты адресатов находятся тем же
   процессом; повторные поиски в течение пяти минут идут без нового запуска процесса (один `postman-plugins.exe`).
5. Простой: пять минут без запросов к каталогу — процесс завершился сам (в диспетчере процесса больше нет; в
   журнале `plugin idle for 5 min, stopped until the next request`); следующий поиск поднимает его снова — без
   ошибок и без перезапуска Postman.
6. Вход учётной записью Windows (компьютер в домене, вход «Учётная запись Windows»): поиск проходит без диалога
   пароля (Kerberos/SSPI — право корпоративной проверки подлинности у процесса набора). Вход по паролю — только по
   TLS: `ldaps://` или StartTLS; пароль — из Диспетчера учётных данных (`Postman:ldap:<сервер>`).
7. Убить процесс из диспетчера во время поиска — запрос отвечает «каталог недоступен», отправка не висит (лимит
   ожидания — 5 с); следующий поиск поднимает процесс.
8. Файла набора рядом нет (переименовать `postman-plugins`) — поиск даёт «проблема с плагином… перезапустите
   Postman» в журнале (`plugin not used: plugin set postman-plugins not found`), интерфейс — «каталог недоступен»;
   вернуть файл — следующий поиск работает без переустановки.
9. Linux/macOS: полный сквозной поиск в автотестах проверяется в потоке теста (loopback песочницы Windows закрыт) —
   настоящий доменный поиск на этих ОС и есть эта ручная проверка; билет Kerberos (`kinit`) или SSSD — по
   `docs/adr/0013` профиль пока не открывает кэш билетов плагину, контроллер домена резолвит интерфейс.
10. Windows: процесс набора со входом учётной записью не падает 0xC0000142 (песочница запрещает win32k; если
    какая-то библиотека LDAP тянет `user32`/`secur32` статически — отложенная загрузка в `build.rs` набора, как у
    Telegram в PLG-05).
